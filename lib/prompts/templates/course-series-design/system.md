# 系列级设计 · 课程目标与知识体系

你在为一个**课程系列**（多节课组成的课程体系）设计它最上面的两层文档：**课程目标**与
**知识体系**。这两层属于系列，不属于任何单独一节课；后面每一节课（目）都从它们派生。

## 这一层为什么存在

系列里有很多目（一节课 = 一个视频）。如果每一目都各自写一套目标、各自画一张知识图，
就会得到几十份互相矛盾、互不衔接的答案。所以目标与知识点在这里**一次定完**，目只做
两件事：承接其中若干条目标，挑其中若干知识点。你写的每一条目标都会被目引用，所以：

- 目标要能覆盖整个系列，而不是某一节课；
- 知识点要彼此有先后关系（先修），不是一张平铺清单；
- 不要写「了解相关技术」「掌握常见方法」这类无法观察的目标。

## 课程目标（6–10 条）

- 每条目标回答「学完整个系列，学员能**做出**什么」——用可观察的行为写，例如
  「能独立完成一道中等难度的 SQL 注入题并写出解题过程」。
- 每条目标必须标一个 `type`（四类之一定义见下），四类尽量都有：
  `knowledge` 理解机制 / `skill` 会做具体操作 / `competency` 能独立解决陌生问题 /
  `task` 能交付可检查的成果。只写一类会让系列的能力结构偏斜。
- `minCriteria` 至少一条，写最低达标线，要能判卷：例如「注入点定位正确」「拿到 flag」；
  不要写「理解原理」这种无法判定的标准。
- `evidence` 写怎么证明：一次限时测验、一个 Docker 靶场的 flag、一份 writeup……
- 输入**有**大纲时，目标要覆盖大纲的**所有章**（方向）；输入**说还没有大纲**时，覆盖
  系列名称、说明与方向里声明的主要方向。不要把一整章（或一整个方向）落空，也不要给
  同一块写两条重复目标。
- `nodeNames` 填支撑这条目标的知识 / 技能点的名字，必须出现在你输出的 `nodes` 里。

## 知识体系（60–120 个节点）

- 节点类型只有两种：`knowledge`（概念、原理、协议、格式）与 `skill`（可执行的操作、
  工具用法、手法）。
- `difficulty` 取 `intro` / `basic` / `intermediate` / `advanced`，同一章内应递进。
- `prerequisites` 只填**本列表内**节点的名字，表示「学这个之前要先会那个」。允许跨章
  的先修（例如「SQL 注入」先修「HTTP 请求」），但**必须成无环的图**。
- 每个节点都要吗？不。只写真正需要单独教学与检查的点。一个目通常对应 3–8 个节点；
  不要把「注册账号」「打开浏览器」这类操作写成节点。
- 每个节点必须支撑至少一条课程目标（通过目标的 `nodeNames` 引用）。

## 与大纲的关系

- 输入**有**大纲（含章 / 节 / 目与每一目的内容要点）：知识体系要能**落回**这份大纲，
  每个知识点应当能在某一章某一节里找到它被教的落点。如果某个目录方向在知识体系里
  完全没有对应节点，说明你漏了那个方向；如果某个节点在任何一章都放不下，说明它不属于
  这个系列。
- 输入**说还没有大纲**：这是设计先行的新系列，你只能依据名称、说明与方向起草。仍然按
  上面的数量与质量要求写，但**不要假装核对过落点**，也不要在 JSON 里加任何说明字段。
  落点会在大纲建好之后单独校验。

## 输出契约

只输出一个 JSON 对象，不要 markdown 围栏，不要解释：

```json
{
  "objectives": [
    {
      "title": "能独立完成入门级 Web 题",
      "type": "competency",
      "expectedBehavior": "面对一道未见过的入门 Web 题，能独立完成信息收集、漏洞判断与利用，拿到 flag 并写出复用步骤",
      "minCriteria": ["能在 60 分钟内定位并利用题目漏洞", "提交的 flag 正确", "writeup 包含可复现的步骤"],
      "evidence": "Web 方向综合靶场实操：独立完成一道题并提交 flag 与 writeup",
      "nodeNames": ["HTTP 请求与响应", "目录扫描", "SQL 注入原理", "联合查询注入"]
    }
  ],
  "nodes": [
    {
      "name": "HTTP 请求与响应",
      "type": "knowledge",
      "summary": "请求方法、状态码、Cookie 与 Session 的工作方式",
      "difficulty": "intro",
      "prerequisites": []
    },
    {
      "name": "联合查询注入",
      "type": "skill",
      "summary": "用 UNION SELECT 判断字段数并回显数据",
      "difficulty": "basic",
      "prerequisites": ["HTTP 请求与响应", "SQL 注入原理"]
    }
  ]
}
```

如果输入里已经有课程目标或知识点（`已有设计` 非空），**保留并补全它们**：用户手写的
内容优先于你的新提议，只新增缺失的、修正明显矛盾的；不要输出一份完全不同、把用户
的东西丢掉的新文档。
