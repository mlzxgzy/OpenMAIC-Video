## 零、一句话结论

现在的界面不是难看，是**把两套并行的产品模型同时摊在一页上，让用户自己挑一条走**。
大修不是美化，是**砍掉平级视图，换成一条任务流**。

## 一、为什么"看一眼没有想法"——诊断

### 1.1 症状与根因的对应

| 用户看到的现象 | 真实根因（代码位置） |
|---|---|
| 进入系列后"铺天盖地" | `curriculum-workspace.tsx` 单页同时挂载：顶部进度卡（6 个 TabTrigger）+ 左侧 4 张卡 + 右侧 6 个 Tab 的**全部内容**。`activeTab` 只控制 `hidden` class（:235），**DOM 全部渲染**，所以视觉上是一堵墙 |
| "不知道下一步干啥" | 顶部"课程体系建设进度"是 6 个**平级** TabTrigger（:710-738），不是流程。真正的依赖顺序只写在文案里（"建课程 → 维护知识点 → 配培养方案 → 组装 → 生成 → 导出"），**界面上没有任何一处声明"现在卡在这一步"** |
| 两套系统不知道走哪条 | `production-path.ts` 已经在**后端**判定了 design / assembly 两条路并给出 `blockedReason`，但 `course-assembler-panel.tsx`（1019 行）和 `design-workbench.tsx`（2122 行）在**界面上是并列的两堆面板**。后端知道，界面不说 |
| 概念是给开发者看的 | 六个名词：课程台账 / 知识体系 / 培养方案 / 课程组装 / 批量生成 / 视频导出。这是**数据模型名**，不是用户任务名。用户想的是"我要做 1-1-1 这一课" |
| 打开即全部展开 | `design-workbench.tsx` 一屏内是 6 个 Dialog 触发器 + 目标×目热力图（`design-heatmap.tsx` 674 行）+ 阶段控件。没有"现在只做这一件事"的收敛 |
| 交付物被埋到最深处 | 真正的交付物是"**一目 = 一课 = 一视频**"，落在 `curriculum_unit(unitRole='lecture').deckDesign → stageId`。但要穿过"组装 → 批量生成 → 浏览器队列导出"三层，每层都是独立页面 |

### 1.2 一句话定性

**这是数据库的浏览器外壳，不是生产台。**
数据模型是对的（七阶段、证据、判分规则都已落地），错的是**没有把已经算出来的状态翻译成人话**。

### 1.3 一个必须承认的事实

后端比前端强得多：

| 已有的能力 | 位置 | 前端有没有用上 |
|---|---|---|
| 7 阶段状态机 + 逐阶段确认门禁 | `design-types.ts` / `curriculum_design_confirmation` | 只有阶段控件，没有"当前阶段 = 你的下一步" |
| 每阶段 AI 对话入口 | `outcomes/turn` `knowledge/turn` `outline/turn` `teaching/turn` `assessment/turn` | 藏在 Dialog 深处 |
| 路径判定 + 阻塞原因 | `production-path.ts:chooseProductionPath` | 完全没露出 |
| 导出闸门 + 已接受缺陷点名 | `design-review.ts` / `export-gate` | 一个角落里的徽章 |
| 28 个阶段化 agent 工具 | `design-tools.ts` + `CURRICULUM_DESIGN_TOOL_PHASES` | **前端一次都没调用** |

所以这次大修**主要是"把已有的判断显示出来"，不是造新能力**。这是好消息：大部分是纯前端重排，API 一行不改。

## 二、大修的总原则

> **一个页面只回答一个问题。系列页只回答"现在做哪个目"，目页只回答"这一目下一步做哪一步"。**

四条硬规则，后面每个设计都受它约束：

1. **一次只有一个主角。** 任何一屏有且只有一个"下一步"大按钮，其余全部降级为次要信息。
2. **状态必须有名字。** 不能只显示 `draft` / `active`，要显示"还没设计""在写教案""卡在审核"并说明**为什么**。
3. **禁用必须给理由。** 沿用 `production-path.ts` 的 `blockedReason` 惯例——禁用的按钮旁边必须有一句话说明为什么禁。
4. **AI 给草稿，人签字。** 沿用 `curriculum_design_confirmation` 的 `user` / `assistant` 区分，界面上必须标明"这是 AI 草的，你确认过"。

## 三、目标信息架构

### 3.1 路由表（最终形态）

```text
/curriculum/series                       序列列表（极简，只做进入）
/curriculum/series/[id]                  ★ 系列驾驶舱：做哪一目 + 54 目矩阵
/curriculum/series/[id]/items            目列表（矩阵的表格视图，二选一）
/curriculum/series/[id]/items/[unitId]   ★ 目工作台：这一目的 7 步流
   ?step=task|outcomes|graph|outline|teaching|assessment|review
/curriculum/series/[id]/items/[unitId]/produce   生成与导出（lecture 才出现）
/curriculum/series/[id]/legacy           旧台账（存档，可搜索，不在主路径）

/curriculum/design/[id]                  保留：直接进入某课程设计的深链
```

星号 = 用户 90% 时间待在这两处。

### 3.2 为什么砍掉"章→节→目逐层下钻"

已确认选择。但**章和节不能消失**——它们是 54 目的分类轴。做法是：

- 章/节从**导航层级**降级为**矩阵的行分组**（`objective-matrix.tsx` 里章是折叠行、节是行内小标题）；
- 目永远是**唯一可点击的最小单元**；
- 面包屑只有 `序列名 › 章节名 › 目名` 一行文字，不做成三层页面。

### 3.3 导航瘦身

现状 5 个入口（`/curriculum`、`/curriculum/series`、`/curriculum/design/[id]`、`/curriculum/courses/[id]`、`/`）互相跳转，目标**只剩 2 个主入口**：

```text
首页  →  继续上次（直达当前卡住的那一目那一步）
侧栏  →  课程序列（唯一列表页）
```

### 5.2 为什么是"左决定 / 右 AI"两栏

现状 6 个 Dialog（`design-outcomes-dialog.tsx` 388 行、`design-knowledge-dialog.tsx` 489 行、`design-outline-dialog.tsx` 412 行、`design-teaching-dialog.tsx` 443 行、`design-assessment-dialog.tsx` 563 行）全部是"全量表单 + 底部按钮"，打开即压满屏。

改成两栏后：

| | 现状 | 大修后 |
|---|---|---|
| 打开瞬间 | 20 个输入框 | 3～6 行待决项 |
| AI 在哪 | 另一个 Dialog / 无 | 右侧常驻，一键起草 |
| 上一步/下一步 | 换 Dialog | 同页切换步骤，位置不变 |
| 长表单 | 需滚动 | 视口内可完成一次决策 |

### 5.3 步骤条设计

> **落地修正（B5，用户实看后）**：本节原来定的"只显示前 4 步、5/6/7 折成「…」"**没有实施**，
> 也不该实施。用户的原话是"还是不够指引，把每一步都标出来，1-7 这种，更加明显一些"——
> 折叠是基于"后三步属于产出模式"的推断，而用户要的是**每一步都能被点名**。落地的是
> `components/curriculum/step-rail.tsx`：七格全显示、大圆圈里写 1..7、当前步写「你在这」。
> 下面保留原方案作为取舍记录。

`CURRICULUM_DESIGN_PHASES` 七步原样保留（后端门禁依赖它，**不能改**）。原方案打算**只显示前 4 步**：

```text
① 任务 → ② 目标 → ③ 图谱 → ④ 大纲 → …（第 5/6/7 步折叠）
```

当时的理由：第 5 步（教学内容）和第 6 步（题目实操）体量最大，属于"进入产出模式"，应该在前四步收尾后用一个**独立的"生成与导出"入口**承载，而不是让用户在七步条里一路往右点。

原折叠规则（**已被否决，勿照此实现**）：

```text
phase ∈ {task, outcomes, graph, outline}  → 条上直接显示
phase ∈ {teaching, assessment}            → 条上折叠为「…」+ 名称提示
phase = review                           → 折叠，且**有未处理 finding 时强制展开并红点**
```

**为什么推断让位**：折叠省下的是版面，代价是"读不出自己走到哪"。用户看不到第 5 步，
就没法把"还要写讲稿"这件事排进今天；而在目工作台里，第 5/6 步恰恰是最花时间的两步。
实际落地见 §8.4。

## 六、AI 副驾（接现有 agent 工具）

### 6.1 三层接入，从轻到重

| 层 | 能力 | 实现 | 成本 |
|---|---|---|---|
| L1 | **意图跳转**（默认） | 前端把一句话映射到 `(目, 步骤)`，直接跳转 + 高亮目标区块 | 低，纯前端 |
| L2 | **调用已有 turn 路由** | 复用 `POST /api/curriculum/design/tasks/[id]/{outcomes,knowledge,outline,teaching,assessment}/turn`，拿回 AI 草稿填入右栏 | 中，路由已存在 |
| L3 | **跨步骤编排**（后续） | 让 agent 连续调 28 个工具走完一步 | 高，需新 agent 会话入口 |

**本轮只做 L1 + L2**，L3 留接口。

### 6.2 L1 意图映射表（前端硬编码，不调模型）

```text
"做 2-1-2"          → 目工作台 · 当前阶段
"写 2-1-2 教案"      → 目工作台 ?step=teaching
"出片 / 导出"        → 目工作台 ?step=produce
"哪些没做"           → 驾驶舱 · 待办区锚点
"出到哪了"           → 驾驶舱 · 看板区锚点
兜底                 → 目工作台 · 当前阶段（最多猜一次）
```

**为什么先不调模型**：这类跳转意图 90% 是关键词命中，调模型的收益低于它带来的延迟和不确定性。L2 才是真正需要模型的场合（起草内容），而那里 turn 路由已经准备好了。

### 6.3 L2 的调用契约

```text
用户点「让 AI 起草」
  → POST /api/curriculum/design/tasks/[id]/knowledge/turn
       body: { message, phase: 'graph' }
  → 200 { rows: [...], shouldConfirm: false }
  → 右栏渲染草稿，逐行标「来源：2-1-1 已有节点」
  → 用户逐行 [采纳] / [改一改] / [丢弃]
  → 全部处理完，底部「确认」按钮才可点
```

**边界**：草稿永远不直接写库。`outcomes-step.ts` 的 `ref` 寻址机制已保证只有命名的行会变；前端再叠一层"未采纳不落库"，双保险。

### 6.4 与 agent 工具的关系

`design-tools.ts` 的 28 个工具是给**对话式 agent** 用的（`CURRICULUM_DESIGN_TOOL_PHASES` 阶段授权）。
前端副驾**不复用**它，而是复用 turn 路由——因为 turn 路由返回的是"可展示的草稿"，而工具调用返回的是"已落库的结果"。这两者需要的中间态不同。

> 若后续要做"整段对话完成设计"（L3），再把 agent 会话挂到目工作台右侧，与副驾并存。

## 七、需要新增的少量后端能力

原则：**能不新增就不新增，必须新增的都写成纯函数并配测试。**

### 7.0 B1 实读后的三处修正（原设计稿写错了）

| 原稿 | 实读结论 |
|---|---|
| `chooseNextItem` 的作用对象是 `CurriculumUnitRecord` | **是 `CurriculumTaskRecord`**。库里 `curriculum_task` 才有 `designPhase`；`curriculum_unit` 是 task 下的章/目条目，一目一门课对应一个 task |
| 54 目矩阵"现有 `GET /api/curriculum` 够用，不用新接口" | **不够**。`CurriculumSnapshot` 是课程产品层，完全不含 design 域；驾驶舱要的是 `objectiveCount` / `blockingCount` / `producedCount`，快照里一个都没有 → 新增 `GET /api/curriculum/design/overview` |
| `FINDING_STATUS_LABEL` 含 `accepted` | 字面量是 `open / resolved / waived`，**`waived` 才是"已接受"**（`resolved` 会被拒收，因为审核是推导出来的）。翻译表按此修正 |

阻塞数在**派生层**算而不是数 `curriculum_audit_finding` 的行：那张表只在显式审核时同步，
一份改过但没点过审核的设计，表里是旧的。直接数行会让"有 3 处阻塞"取决于用户上次什么时候
点了审核，而界面不会说这件事。`overview` 改为读快照重新派生，代价是每目一次审计，
换来这个数字与导出闸门口径一致（路由测试第 1 条钉住）。

### 7.1 54 目矩阵的取数

见 §7.0：`GET /api/curriculum/design/overview?seriesId=...`，逐字返回聚合行，
**不做推荐**。推荐是纯函数的事，混进服务端就会让"继续上次"和驾驶舱各算一遍。

### 7.2 新增纯函数 `chooseNextItem()`

放在 `lib/curriculum/next-item.ts`（已有同类先例：`chooseProductionPath`）。

```ts
export interface NextItemRow {
  taskId: string;
  code: string | null;
  title: string;
  phase: CurriculumDesignPhase;
  unitCount: number;      // 章 + 目，用来判断这还是不是一副骨架
  producedCount: number;  // stageId 非空的目数，> 0 即已出片
  objectiveCount: number; // 为 0 表示第 2 步还什么都没定
  blockingCount: number;  // 未被接受的 error 级发现数
  updatedAt: string;
}

export function pendingItems(rows: readonly NextItemRow[]): NextItemRow[];
export function chooseNextItem(rows: readonly NextItemRow[]): NextItemDecision | null;
```

排序规则（已写死并配 10 条测试）：

```text
1. 有 open error finding 的目最优先（阻塞出片，必须先解）
2. 其次：正在设计的目（阶段≠task 或已有目标/条目），按 updatedAt 降序 —— 这就是"继续上次"
3. 再次：还没开始的目，按 updatedAt 升序（最早建的先做）
4. 已出片（producedCount > 0）的目永不入选
```

**`pendingItems` 与 `chooseNextItem` 共用一个比较函数**，因为驾驶舱同时显示"推荐一
目"（大卡片）和"一列待办"（左栏），各自写排序就会得到两个不同的第一条，而用户
无从判断哪个是系统的想法。这是最容易在重构中被"顺手统一"掉的一处，测试里有一条
断言二者的第一条恒等。

理由用**三种措辞**（阻塞 / 进行中 / 未开始），因为它们要求用户做的事根本不同：
修东西、接着干、开个头。混成"继续完成 2-1-2"就是"看一眼没有想法"的成因。

### 8.0 B2 试点落地后的实读修正

原稿的 L2 契约假设 turn 路由能返回"可展示的草稿"。**它不能**：`POST .../knowledge/turn`
是"模型说完就直接写"的路由，它的回包是**写完之后**的图。所以试点没有改它的契约，而是
新增了一个 `POST .../knowledge/draft`——同一个模型、同一套确定性规则（ref 解析、环检测、
整表合并），**一行都不写**。原稿"不改 turn 路由契约"这条仍然成立，代价是多一个起草路由。

原稿说"采纳走已有手工路由"，这一点比想象的重要：它让"采纳"与"手工新建"是**同一件事**，
于是阶段校验、端点归属校验、链接整表替换规则都自动覆盖 AI 这一侧，界面上也不存在
"AI 那条路少了一层校验"。

试点中被实读与 e2e 抓出来、已写进代码注释的三处：

| 原稿假设 | 实读结论 |
|---|---|
| `turn.links` 是"AI 想改的连线" | 它是**这一轮之后的整份集合**（没提到的节点也带回来）。当成建议画出来就是满屏噪音 → 只画与动手前**有差**的那些 |
| 采纳新节点时发它自己的连线 | `setCurriculumNodeObjectives` 是**全表替换**，少发一条就是一次静默删除 → 采纳时必须带当前全部连线（`mergedLinkSet`） |
| 草稿字段直接发出去 | `POST /nodes` 的 `readNode` 用 `oneOf` 读难度，**发了 `null` 会 400** → 空的摘要与难度整个键不发（`nodeDraftForAdoption`） |

**另一处不是原稿写错，而是原稿没提、但必须做的边界**：工作台的 `run()` 会把失败吞进
页面的错误条然后正常返回，所以最初版本会让右栏一边显示"已采纳这一行，左栏已经改好"、
一边什么也没写进去。采纳改为**不经过 `run`**，失败抛回右栏——采纳记录与存储必须由同一次
结果决定。这个 bug 只有 e2e 逮到（"已采纳"可见但库里是空的），三条单元测试全绿。

### 8.2 五步铺开（B3）：从"知识技能图那一套"到"一副骨架"

§8.0 的试点只有第三步有这套交互，而**五步的交互本来就是同一件事**：出草稿、逐行签字。各写
一套的代价不在第一份，在第五份——"采纳一行"的语义（多跳、依赖、整表替换在采纳那一刻重算）
会在五个文件里各演化一次，而这五处全都是"作者以为库被改了、实际上没有"的那一类错误。

落地形状：

| 层 | 文件 | 职责 |
|---|---|---|
| 引擎 | `lib/curriculum/step-draft.ts` | 行 = {打哪个路由、带什么 body、依赖谁}。**不认识任何领域概念** |
| 骨架 | `lib/server/curriculum/step-draft-route.ts` | 同源校验、阶段门、错误映射、回包。上下文类型里**没有 `write`** |
| 面板 | `components/curriculum/step-copilot.tsx` | 出草稿、逐行签字。没有第二个写库入口 |

`docs/curriculum-redesign/workbench-copilot.png` 是第三步右栏的实际样子（真界面截图，
不是线框）：三类行一眼可分——可按的（采纳/改一改/丢弃）、要等别的行先落地的（按钮灰掉，
理由写在行上「先采纳「新知识点「目录枚举」」，这一行才有要填的东西」）、以及**说明行**
（`没找到「WAF 绕过」`，没有按钮）。顶部那句「还有 2 行等你决定」只数前两类：说明行没有
"决定"这回事，数进去这句计数就永远到不了零。
| 转换 | `{outcomes,outline,teaching,assessment}-draft.ts` + `knowledge-draft-lines.ts` | 每一步唯一的领域知识 |

**"草稿不落库"从自觉升级成类型不变量。** 试点里这条靠一条"源码里没有 `ctx.write`"的测试钉着
（那条测试还在，降级为回归）；现在骨架交给步骤的上下文是 `DesignContext` **去掉 `write`** 的
那部分，加一次写库连编译都过不了。四个 `*/draft/route.ts` 由一条扫描 `tasks/**/draft/route.ts`
的测试逐个检查，所以"忘了走骨架、自己写一遍 handler"会立刻变红。

**这一步实读抓出来的两处，都不是设计稿写错，而是通用化本身引入的：**

| 现象 | 根因 | 怎么发现的 |
|---|---|---|
| "改一改"在界面上改得动、库里还是模型给的原名 | `renamed()` 返回新对象而**不改入参**；通用化时新建那条路写成 `renamed(body);`，返回值被丢掉。单元测试当时只覆盖了 `write` 那条路，全绿 | e2e 读数据库 |
| 一道"模型没标 Bloom 层级"的题**永远采纳不了** | `QuestionWrite.bloomLevel` 在模型没写时就是 `null`（`draft.bloomLevel ?? null`），而 `POST /questions` 用 `oneOf` 读它——显式 `null` 报的是"只能是以下之一"，与这条建议毫无关系 | 读路由校验层时发现，随后用真实路由测试证明（带 `null` 400、不带 201） |

第二处是 **B2 那个 bug 的同一个形状**：试点修了 `POST /nodes` 的难度，只修了**新建**那条路，
而 `PATCH /nodes/<id>` 用同一个 `oneOf` 读难度，`PATCH /questions/<id>` 也一样。所以这一条现在
是 `lib/curriculum/draft-body.ts` 里的一个共用来回，而不是每处各写一遍的判断：

- 名单从 `design-validation.ts` 的源码里读出（全部 `r.oneOf(...)` 键），有一条测试盯着"新增一个
  枚举字段忘了加进名单"；
- 引擎在**发出去之前**再兜一次，所以六个步骤与将来第七个都不可能发出这种 body；
- 被丢掉的如果是"清空这一项"（改写路径上发 `null` 的原意），它会变成草稿的一句 `warnings`——
  那一行仍然会成功，所以不说出来就是一个看不出来的半执行。

### 8.3 旧 Tab 的去向（B3 尾段，已落地）

**归档。** 6 Tab 台账整体搬到 `/curriculum/legacy`（`app/curriculum/legacy/page.tsx`），顶部一条
存档横幅说明"日常做课的顺序是：课程序列 → 系列驾驶舱 → 这一目"，页头加了「去课程序列」。
`/curriculum` 变成一个 `redirect('/curriculum/series')`——不删这个路径，是因为它在浏览器书签、
外部链接与旧文档里都已经存在，删掉会得到一个 404。

主路径上的入口同步收敛：`series-workspace` 页头那个「全部课程」主按钮**删掉**了（它指向的正是
"看一眼没有想法"的那一页），换成页脚一句小字；驾驶舱页脚的链接改指向 `/curriculum/legacy`。

**只迁「生成与导出」，已落地为目工作台的第三个 Tab**（`components/curriculum/design-produce.tsx`）。
原来设计编辑器把七步做完之后，这个页面上**没有任何一个按钮能拿到视频**：要先去旧台账的「课程组装」
找到同一个设计、点生成，再去「视频导出」排队。现在这一目的条目、门禁结论、每条生成的 run 状态
和导出任务都在同一页。

这一迁移带出三处只有跨层才看得见的东西：

| 现象 | 根因 | 怎么发现的 |
|---|---|---|
| 点「导出 MP4」什么也没发生 | 那一行显示的 stage 来自**刚跑完的 run**（`unit.stageId ?? run.stageId`），而 handler 里现读 `unit.stageId`——生成 hook 还没把 `stage_id` 写回库。界面看到的和发出去的是两个来源 | e2e 读队列 |
| 导出队列多出一种来源，却一条服务端测试都没有 | 批量导出原来只有"入队"和"读取"是服务端的事，而这两条路之前**完全没有测试** | 加 stage 入队时发现 |
| `/curriculum/legacy` 的 Tab 名字不能用全名匹配 | `TabsTrigger` 里还挂着这一块的说明文字，可访问名字是"课程台账 先建系列和课程"整串 | e2e strict mode |

**导出按 stage 入队**（而不是先造"批量项"）：`curriculum_export_job.batch_item_id` 本来就允许
NULL，而认领与 worker 只读 `stage_id`，所以"设计直接产出的课堂"是一条普通任务，不需要新表。
`POST /api/curriculum/export-jobs` 现在收 `{ stageIds, stageTitle }`，并且**逐 stage 幂等**——
已有未失败任务的 stage 原样返回，不排第二条 MP4。`GET /api/curriculum/export-jobs?stageIds=`
是新的读取路径，目工作台靠它看到自己那几个课堂的进度。

浏览器侧的认领/构建 ZIP/提交渲染/轮询抽成了 `lib/curriculum/export-worker.ts` 一份实现，两个页面
共用。这不是省代码：认领是**按 owner 取全局最旧一条**，两个页面本来就会互相认领对方排的队；
各写一份，一份修了"被中断的 building 任务"另一份没修，就会出现只在某个入口复现的"导出永远卡住"。

**B4 也做了：首页「继续上次」**（`components/curriculum/continue-last-card.tsx`）。它调的是驾驶舱
用的同一个 `/api/curriculum/design/overview`，排的是同一个 `chooseNextItem`。三条边界：没有待做的
一目时整块不渲染、接口失败静默隐藏（首页不能因为一次附带读取失败而报错）、读取期间不出占位
（它在 2×2 入口网格上方，出了占位会让下面两块按钮跳一次位置）。

### 8.4 七步条（B5，用户实看后）

B1–B4 落地后用户的原话是：**"还是不够指引，把每一步都标出来，1-7 这种，更加明显一些"**。
指的是上一版的步骤指示：`design-workbench.tsx` 里的 `PhaseRail`——一排小号徽章、**没有序号**、
只长在编辑器那一半的顶部，而且只有第 1 张卡片写着"（第一步）"。滚到第三张卡片时，页面上
没有任何一处说得出"这是第 3 步、前两步签过了、后面还有四步"。

改法是一根共用组件 `components/curriculum/step-rail.tsx`：

| 决定 | 为什么 |
|---|---|
| **七格全显示**，不再折叠 5/6/7 | §5.3 的折叠规则是设计者的推断（"后三步属于产出模式"），用户要的是每一步都能被点名；`STEP_BAR_PHASES`（只含前四步的常量）随之删除，留着它下一个人会照着改回去 |
| 步骤条挂在 `DesignTaskShell` 的 **Tabs 之外** | 矩阵、编辑器、生成与导出是同一目三块材料；只长在编辑器里，切到矩阵（审核那一步发生的地方）就失去方向 |
| 大圆圈里写 **1..7**，名字在下 | 序号是主角：不读文字也能答"我做到哪了" |
| 三种状态**不只靠颜色** | 已走完是对勾、当前是实心 +「你在这」、没开始是空心圆——色盲、灰度、截图里都读得出 |
| 编辑器每张卡片带 **「第 N 步」角标** | 卡片是纵向排开的一条长页，离开顶部几百像素后步骤条已滚出视野 |
| 驾驶舱推荐卡里也放同一根 | 它以前只在按钮旁写一行 `text-xs` 的"这一步是第 ③ 步"，正是用户说的"不够指引" |

顺带修掉一处重复：`chooseNextItem` 的理由原本是 `卡在第 3 步 · ③ 需要哪些前置知识。`——序号
出现两遍（"3"与"③"），而且与旁边的七步条、标题角标说的是同一件事，一屏三遍。现在理由回答
**"为什么是这一目"**（"这是最近动过、还没出片的一目"），步骤交给步骤条结构化显示。
`next-item.test.ts` 相应改为钉住"理由里不出现步骤名"。

待办行的同类问题一起修了：以前"有阻塞"时把步数**整条换成**"N 处审核未处理"，于是一半的
行读不出进度——两件事并不互斥，现在都显示。

### 8.5 一次步骤引用必须带序号（B5 尾段）

七步条上线后，用户贴回一张目工作台的截图：**同一个第 3 步，一屏里有四个名字**。

| 位置 | 原文 |
|---|---|
| 卡片标题 | 第 3 步 知识技能与依赖 |
| 空态小字 | 先完成**依赖图**阶段，才能新建知识点。当前在**学习成果**阶段。 |
| 右栏红字 | 课程任务当前处于「**outcomes**」阶段；先确认前面的步骤并推进到「**graph**」阶段，再来知识技能图起草 |
| 确认按钮 | 确认**知识技能图** |

四个都不是打字错误，是**四份各自维护的文案**——卡片名一份、`design-knowledge.ts` 的缺口一份、
`design-store.ts` 的阶段门禁一份、按钮一份。所以加一根步骤条解决不了它：只要还有第二份文案，
就一定有第四个名字。

规则因此写成一句话，并且**由测试执行**（`tests/curriculum/step-labels.test.ts`）：

> **用户可见的每一次步骤引用都必须经过 `stepRef()`**，序号与名字一起出现。

| 改动 | 为什么这么做 |
|---|---|
| `ui-labels.ts` 增加 `STEP_WORK_NAME` 与 `stepRef()` / `stepLockReason()` / `stepLockMessage()` | 步骤名、序号、句式的**唯一**出处；`ui-labels.ts` 是纯字符串映射，不 import 服务端，所以路由、store、组件都能用同一份 |
| 五处 409（`step-draft-route` + 三条 turn 路由 + `store.assertPhase`）改走 `stepLockMessage` | 原来直接插 `task.designPhase`，把数据库里的 `outcomes`、`graph` 倒进中文句子；`assertPhase` 那句还会经路由回给客户端，用户看得到 |
| 六条阶段缺口文案（`design-store` 的 `phaseCompletionGaps`）改由 `STEP_WORK_NAME` + `stepRef('next')` 拼 | 原文是"学习目标与考核标准还没有确认（确认后才会进入知识技能图阶段）"，一句话两个旧名字 |
| 十一个 signoff / dialog 的按钮与提示语改走同一张表 | 「确认知识技能图」与卡片标题「知识技能与依赖」不再是两个词 |
| 门禁的 `新建${label}` 换成逐条写的 `action` | `coverage`、`unit-dependencies` 是**关系**不是新行——"新建教/练/考覆盖"读起来像在库里插一条记录，实际动作是"勾上"和"排一条"；用户要照着这句话做事，动词错了指引就是反的 |
| 源码扫描用例：`进入X阶段`、`旧名词+阶段`、`「${…phase…}」` 三种形状在 `components/`、`app/`、`lib/` 里必须为 0（跳过注释行） | 钉住的是**形状**而不是某一句文案；另有一条正向用例，点名八处拼步骤引用的文件必须真的调用 `stepRef`/`stepLockMessage` |

**顺带**：`design-outline-signoff` 与 `design-teaching-signoff` 的 `blockers` 没有去重，而这一步的
缺口与 error 级审核发现常常是同一句话（"还没有任何条目…"），确认按钮的悬浮说明里会把同一句念
两遍；`design-assessment-signoff` 早就用了 `new Set`，现在四处一致。

走查脚本 `scripts/verification/ux-step-labels.mjs` 把这个状态造出来（方向已确认并前进到第 2 步），
逐条核对：步骤条说的是第 2 步、只有一个 `[data-step-state="current"]`、每张卡片角标都带
「第 N 步 / 共 7 步」、被挡住的按钮说得出"到第几步、做什么"、界面上没有旧名字与阶段字面量、
直接点「让 AI 起草」得到的红字是步骤语言、窄屏下七格一行且可横向滚动。

### 8.6 先出章、再出节、最后出目（§3.2 的修正）

§3.2 已经拍板"不做章 → 节逐层下钻"，理由写在那里：章/节从**导航层级**降级为矩阵的行分组，
目是唯一可点击的最小单元。那个决定没有变——本期新增的是**创建顺序**：章、节必须能在任何目
之前存在，否则"新建目"就是一个没有槽位的填空题。

用户的原话是"我的印象里这个项目应该是先出章再出节，然后最后再出目的吧，现在直接让我写目，
我怎么写啊"。诊断：章和节以前只存在于**每个目内部**的大纲（`curriculum_unit` 的
`chapter`/`item` 两级，靠 `parent_id` 分层），而驾驶舱的章分组是拿目编号前缀猜的——
`series-cockpit.tsx` 的旧注释自己写着"库里没有'目属于哪一章'这个字段，这是一个**明确降级**"。
编号还要等第 4 步填了第一个条目才出现，所以创建时连"这是 1-1-2"都不知道。

| 决定 | 内容 |
|---|---|
| 大纲独立于目 | 新表 `curriculum_series_outline_node`（`chapter` / `section`，migration 15）。可以为空系列先建 6 章 18 节，再逐节建目 |
| 目挂到节上 | `curriculum_task.section_id`（`ON DELETE SET NULL`：删节不删目，目退回"未归类"）、`code`（`2-1-2`）、`kind`（理论/实操/综合）、`order_index` |
| 系列默认 brief | `curriculum_series.audience / default_hours`；新建目时继承，仍可在第 1 步覆盖——让用户对着五十四目各填一遍培训对象，得到的是四份互相矛盾的答案 |
| 驾驶舱按状态换主角 | 没有章 →「先把大纲搭出来」（建第一章 / 从大纲导入）；有章没目 →「建第一目」；有目 →「现在做这一目」 |
| 推荐顺着大纲走 | `NextItemRow.outlineRank = 章序×10000 + 节序×100 + 目序`，仅用于"还没开始"那一档；进行中仍是"最近动过"优先 |
| 导入是纯文本 | `lib/curriculum/outline-import.ts`：`#` 章、`##` 节、`-` 目（`编号 | 标题 | 类型 | 学时 | 要点`，除标题外可从右往左省略）。先 `preview` 再 `commit`；有解析错误、系列已存在大纲或已存在目时整批拒绝 |
| 词表去重 | 目内条目角色改称「讲授 / 练习 / 考核」（`UNIT_ROLE_LABEL`），目的类型才叫「理论目 / 实操目 / 综合目」（`ITEM_KIND_LABEL`）；第 4 步的 AI 开场白改成"这一目就是一节课，排成条目，分组可选" |

**仍然不做的事**：不新增 `/series/[id]/chapters/[chapterId]` 这类三级页面。大纲树是驾驶舱
**同一页**上的编辑区与看板，点开任意一目仍然直达目工作台。§3.2 的导航决定原样成立。

**数据库把形状钉住**：章必须 `parent_id IS NULL`；节的父级必须是同一 owner、同一系列的一章
（CHECK 管不了跨行，所以 migration 15 建了触发器 `curriculum_outline_node_parent_guard`）；
编号在系列内唯一（`WHERE code IS NOT NULL` 的部分唯一索引）。删节让目 `section_id` 置空，
删系列级联删大纲节点（分类没了，目跟着变成未归类而不是消失）。

`tests/curriculum/series-outline-route.test.ts`（13 条路由契约，含"预览不写库""重复导入 409"
"删节不删目"）、`tests/curriculum/series-board.test.ts`（6 条目录叠加，含空节与未归类）、
`tests/curriculum/outline-import.test.ts`（12 条解析，逐行报错）、`next-item.test.ts` 补两条
大纲顺序用例。种子文件 `course-packages/ctf/outline-54.txt`（6 章 18 节 54 目）已导入
`series-0mEIJmhYzltN`，54 目编号、类型、学时、brief 草稿全部落库。

### 8.7 AI 生成大纲：三个按钮，一次一级

用户的原话是"添加个 ai 生成的功能，根据系列名称和系列说明自动生成章节目，注意章节目都
分开，也就是说 3 个 ai 按钮，再帮我考虑考虑现有内容的清空，点了 ai 该怎么处理"。

三个问题分别有一个决定：

| 问题 | 决定 |
|---|---|
| 为什么是三个按钮，不是一个"一键生成全套" | 章、节、目是三种不同粒度的决定：章是方向，节是案例，目是一节课。一次让模型吐三层，它会为了凑结构编造"每章三节、每节三目"，而用户没法只否掉其中一层。三个按钮各带一次模型调用，输入是**已经存在的那一层** |
| 点了 AI，已有内容怎么处理 | 默认只补空位（fill）：章=追加不重名的新章；节=只给还没有节的章生成；目=只给还没有目的节生成。覆盖重建（replace）是显式选项：章/节一旦系列里已经有目就不允许（目会失去归属），目这一层只覆盖 `design_phase='task'` 且没有任何下游数据的目 |
| 从点到写，中间有什么 | 两步：`preview` 调一次模型、只算"新增 / 删除 / 跳过"、不写库；`commit` 带回用户看过的那份 plan，在**同一个事务**里重读现状、重算（strict：预览之后大纲变过就整批拒绝）再写。commit 不再调模型，所以两次点击不会生成两份不同的东西 |

**覆盖的代价写进界面，而不是写进报错。** 重建章/节只在系列里**一个目都没有**时可选；
有目时按钮直接禁用并给理由（"已经有 54 个目，重建章会让它们全部掉进「未归类」"）。目这
一层允许覆盖，但删除对象只有"还没开始设计"的目——判据不是 `design_phase` 一个字段，而是
逐表 `NOT EXISTS`（objective / evidence / learning_node / unit / question / lab_task /
audit_finding / design_confirmation）：第一步之前同样是 `task`，但那时可能已经有草稿数据。

**预检先于模型调用。** "每一章都已经有节"这种问题一秒钟就能从现状读出来，不该花一次模型
预算去发现。`seriesOutlineAiPreflight` 在调模型之前判掉这些情况，且它是 `plan…Apply`
计算目标的唯一来源——两处各算一遍，预览和写入迟早给出不同结论。

**引用用编号，不用 id。** 模型返回 `2` / `2-1`，那是用户在大纲里核对的同一串字符；找不到
或目标已不在生成范围时，预览降级为警告，提交阶段直接拒绝（绝不"写了一半"）。

| 文件 | 职责 |
|---|---|
| `lib/curriculum/series-outline-ai.ts` | 纯函数：解析模型回答（容忍围栏/废话、上限即拒绝线）、预检、写入计划、提示词上下文 |
| `lib/server/curriculum/series-outline-step.ts` | 一次模型调用 → 一份计划；坏 JSON 重试一次 |
| `lib/server/curriculum/series-outline-ai-validation.ts` | 该路由的请求体校验（独立成模块，避免一次新增让几十个共享路由一起重编译） |
| `lib/server/curriculum/series-outline-ai.ts` | 读现状（含"目是否还能被覆盖"的新鲜度判定）与事务内落库 |
| `app/api/curriculum/series/[id]/outline/ai/route.ts` | `preview` / `commit` 两个动作 |
| `lib/prompts/templates/course-series-{chapters,sections,items}` | 三份提示词：章=方向、节=案例、目=一节课 |
| `components/curriculum/outline-ai-dialog.tsx` | 三个按钮共用的对话框：系列说明、处理方式、预览、写入 |
| `lib/curriculum/series-outline-ai-client.ts` | 两个请求 + 保存系列说明 |

**验证**：`tests/curriculum/series-outline-ai.test.ts`（21 条：解析、预检、fill/replace、
strict 拒绝、提示词变量、交底向下传递）、`tests/curriculum/series-outline-route.test.ts` 新增 9 条
路由契约（预览不写库、提交建章/节/目、建模之后**不调模型**、覆盖护栏、目覆盖只删未开始的目、
坏 JSON 502、缺 plan 400、404）。

### 8.8 备注不是摘要，是交给下一层的「交底」

用户的原话："章节目生成的逻辑有点脱离了……每层生成的时候，都加个备注，让下面建立的
内容不脱节。"

上一版三层的备注都生成了、也写进库了，但生成链路里**只有标题在流动**：生成节时提示词里
只有章标题，生成目时只有节标题（`SeriesOutlineAiSection` 连 `note` 列都没读）。所以三层
各自都通顺，合起来却对不上——章里写"拆 3 节：信息收集、注入、文件与逻辑漏洞"，生成节时
模型看不到这句话，只能按标题猜。

决定：**备注就是三层的上下文通道，界面上叫「交底」**。每层只写一件事——这一层的决定如何
约束下一层：

| 层 | 交底内容 | 谁读它 |
|---|---|---|
| 章 | 学完能做什么、覆盖哪 2–5 个互不重叠的内容面、边界（不包含什么 / 与相邻章的区别）、建议拆几节与每节案例 | 生成节 |
| 节 | 案例 / 任务（点名对应章交底的哪个内容面）、2–4 个目的分工（理论讲什么、实操练什么、综合复盘什么）、3–6 个内容要点、同章边界 | 生成目 |
| 目 | 3–6 个内容要点，只写这一目要解决的问题 | 这一目第 1 步的 brief 草稿 |

传递方式很直接：`handoffLine` 把 `章交底` / `节交底` 原样写进 `outlineTree` 与 `targets`
两个提示词变量——`targets` 里每个目标都带父级交底，`outlineTree` 里每个已有章 / 节都带
自己的交底。**没有备注时给明确占位**（"还没有备注，按标题与系列说明判断"），不是留空：
留空会让模型把"没有约束"当成"可以自由发挥"。

看板显示章 / 节的交底（两行 + `title` 全文）：用户接下来点「AI 生成节 / 目」时，模型看到
的就是这句话，备注写偏了下一层必然跟着偏。

**验证**：纯函数 2 条（章交底进生成节的 `targets`/`outlineTree`、节交底进生成目的
`targets`、没有备注时的占位）；路由契约 2 条（AI 生成节 / 目时，`callLLM` 收到的 `prompt`
里真的带着章交底、节交底）。活体验证（真实模型 + 临时系列）：章交底写"拆 3 节：信息收集、
注入、文件与逻辑漏洞"，生成节**恰好 3 节**且每节首句都在说"对应章交底的某一面"；提交后
生成目，9 目按 3 节 × 理论/实操/复盘 铺开，内容要点与节交底逐条对应。临时系列已删除。

### 8.9 七步里哪几步属于系列，哪几步属于目

用户的原话："现在我生成出来 60 多个目，按照现在的功能来说，每个目都有 7 步需要做？？？
是不是有些步骤的目标其实是课程系列，而不是目啊。"

答案是：**第 1–3 步属于系列，第 4–7 步才属于目。** 七步模型是按「一门课」设计的，而在一个
系列里「一门课」是目；于是同一个七步在 63 个目上各走一遍，得到的是 63 份互相矛盾的受众、
63 套互不相连的知识图——不是 63 份答案。

| # | 步骤 | 真正的归属 | 目做什么 |
|---|---|---|---|
| 1 | 课程方向（受众 / 基础 / 场景 / 范围 / 学时） | **系列** | 继承；只在目自己有差异时覆盖 |
| 2 | 学习目标与证据 | **系列**定课程目标；目承接其中若干条 | 从系列目标派生本目目标，不重造一套 |
| 3 | 知识体系与先修 | **系列** | 在系列知识体系里挑本目要讲的点 |
| 4 | 大纲 | 系列大纲层已有章 / 节 / 目；目只排内部条目（讲 / 练 / 考） | 条目结构 |
| 5 | 授课脚本与分镜 | 目 | 一节课的讲稿与页面 |
| 6 | 题目与实操 | 目 | 本目的题与 Docker 任务 |
| 7 | 审核 | 目（系列层另做跨目汇总） | 本目自审 + 导出闸门 |

落地分两层，这一轮做的是上层与继承：

**系列层（这一轮新增，migration 16）**：`curriculum_series` 补方向列与两列 JSONB
（`course_objectives` / `knowledge_system`），新页面 `/curriculum/series/[id]/design`
一次做三件事——方向、课程目标与证据、知识体系。课程目标必须写可观察行为 + 最低达标线 +
证明方式；知识点支持先修（写入时拒环）；两者都可以「AI 起草」（一次生成两层，因为目标
引用节点、节点支撑目标是同一份文档的双向引用）或「编辑文本」（`## 标题` 块格式，人改的
与模型写的走同一套解析）。JSONB 而不是五张新表：形状由作者决定，没有需要数据库守的外键，
唯一要守的两条（引用存在、先修无环）在写入时校验，报错比库约束可读。

**目的继承（这一轮新增）**：新建目时从系列方向复制受众 / 基础 / 训练场景 / 应用场景 /
学时；门禁 `phaseCompletionGaps('outcomes')` 读的是**有效值**（目列 ?? 系列列），所以
"目先建、系列方向后补"也能离开第 1 步。这一条修的是一个真实死锁：63 个目的 `audience`
全为 `null`，而 `audience` 是离开第 1 步的硬条件——按旧逻辑，每一目都要手工再填一遍
同一个受众。有效性在**三个入口**同源：目快照（卡片显示）、方向确认路由（POST 的完整性
检查）、方向对话路由（模型看到的卡片）。三处里漏一处，就会出现"卡片说缺授课对象、
点确认却推不动"或反过来的分裂——所以它们都调用 `effectiveDirectionValues`。

顺带修掉一个只在浏览器里看得见的分裂：快照此前只带目的列值，系列填了受众、目留空时
卡片仍会显示"缺授课对象"并禁用确认按钮；现在快照带 `seriesDirection`，卡片按有效值
显示与判断，并在字段标签上标「（继承系列）」。

**目层（§8.10 已落地）**：第 2/3 步从"重建"改成"承接选择"。实现上没有做跨 scope 外键，
而是**复制 + 来源 id**（理由与代价见 §8.10）。

**验证**：规则层 20 条（归一化、校验、阶段、文本往返、AI 回答解析、继承与有效值）；
路由契约 9 条（真实 PGlite：保存三层、坏目标 400、先修成环 400、跨 owner 404、AI 只回
草稿不写库、无大纲不花模型预算、新建目继承系列方向、后补方向门禁也认、后补方向后
确认按钮也认）；migration 16 已 pin 进 checksum 金标并应用到开发库。另外在**运行中的
dev server**上做了一次真实链路自检：建临时系列 → 保存方向 → 建章 / 节 / 目（目继承受众
与学时）→ 目快照带 `seriesDirection` → 确认第 1 步 → 推进到 `outcomes` → 删除临时数据。

### 8.10 目层：第 1 步只读继承，第 2/3 步从系列承接

用户的下一条反馈更具体："进入某个系列 → 大纲编辑 → 某个目 → 内容编辑 → 设计编辑器，
咋又是课程方向和目标和大纲？这个不是说放到课程全局去吗？…… 七步里哪些是针对课程系列，
哪些是针对目的，都给我重新审一下，现在这个系统越来越乱了。"

先把事实摆出来（重构前的真实浏览器走查，`artifacts/regression/seven-step-audit/`）：
目编辑器里排着九张卡片，覆盖全部七步——课程方向（七个可编辑输入框）、学习目标与证据、
知识技能与依赖、课程大纲、教/练/考覆盖、授课脚本与分镜、题目与实操、测验题、实操任务。
七步本身没错，错的是**没说清哪几步是系列给的**，而且第 1 步让用户把系列已经定过的受众
再填一遍。

这一轮的修法，四处：

**1）归属表进代码，界面只渲染不判断。** 新增 `lib/curriculum/step-ownership.ts`：
七步各自的 `owner`（`series` / `item`）与 `itemDuty`（`inherit` / `select` / `own`）。
步骤条分组、目编辑器横幅、第 1 步卡片、文档全部读这一份。写在别处会出现"步骤条说是
系列的、卡片却让人编辑"这种只在界面上看得出来的矛盾。

**2）步骤条分成两段。** 「系列层（定一次，所有目共用）」3 格 + 「本目（每一目都要做）」
4 格，序号仍是连续的 1..7——分组说明归属，不改变流程顺序。外层容器保留
`data-testid="step-rail"` 与七个 `li[data-step-state]`，现有断言不改。

**3）第 1 步默认只读。** 有系列时，卡片把七个字段渲染成静态列表并标出来源
（`（系列）` / `（本目改过）` / `未填写`），七个输入框退到「本目确实不同，覆盖」后面。
同时课程范围（`problemStatement`）也改成继承——这一条之前被刻意排除（注释说"属于目"），
结果是六十多个目各填一遍同一个范围。来源按**值**判断而不是"任务行那列是不是空"：建目时
会把系列方向复制进任务行（审核与提示词直接读任务行），列非空不等于作者改过。

**4）第 2/3 步变成「承接」。** 目工作台里新增承接面板（`series-inherit-panel.tsx`）：
列出系列里的课程目标 / 知识技能点，勾选后一次写进这一目。配套
`POST /api/curriculum/design/tasks/[id]/inherit`（`{kind:'objectives'|'nodes', ids}`）。

承接的三条设计决定：

- **复制 + 来源 id，而不是跨 scope 引用。** 目里的目标要挂证据、节点要挂条目、题目与
  审核都拿这些行当地址；系列设计是 JSONB，没有行可以当外键。复制一行、再用
  `series_objective_id` / `series_node_id`（migration 17）记住来源，是"能当地址"与
  "知道来自哪"之间最省事的一种。存 id 而不是标题：改标题不会脱钩，按钮也能幂等。
  代价是**系列改了之后已承接的行不会自动更新**——这是下一步要解决的（要么做差异提示，
  要么改成引用）。
- **承接时一起建证据。** 离开第 2 步要求"每个目标都有证据"。只复制目标的话，用户
  "承接完了"照样被门禁拦在"目标没有证据"上——一个承接按钮反而制造更多工作。所以按系列
  目标声明的方式生成一条本目证据（`performance`，唯一不预设形态的类型）。
- **节点承接时自动连线。** 系列目标声明了它由哪些节点支撑；这一目已经承接了某些目标时，
  新节点立刻连上它们，否则第 3 步门禁报"节点不支撑任何目标"。

顺带改名：第 4 步从「课程大纲」改成「**本目大纲**」。系列层也有一个「大纲」（章 → 节 →
目，在驾驶舱维护），两个同名物放在一起正是"越来越乱"的直接来源。

### 8.11 先系列设计，后大纲：大纲以系列设计为依据

用户看完 §8.10 后的判断很直接："现在进系列直接进大纲了，是不是应该先进系列设计，
前三步设计好了再去大纲，然后大纲根据系列设计的内容来出？"

是。§8.9 已经把前三步上移到系列，但**入口顺序与生成依据没有跟着改**：新系列依然
直接落在驾驶舱，AI 大纲依然只读系列名称与说明。结果是"课程目标定好了，大纲却从
标题猜"——正是 §8.8 说过的"三层各自通顺、合起来对不上"在系列层面的重演。

这一轮四处改动：

**1）入口门禁：空系列先落到系列设计。** 驾驶舱加载时同时读设计快照；当
`没有章 && 前三步未定完` 时 `router.replace` 到 `/curriculum/series/[id]/design`。
跳转期间不把 `loaded` 置真，避免先闪一下"空大纲"的驾驶舱。
**已经有大纲的系列不跳转**：那是历史数据，藏起来等于把用户做出来的大纲弄丢；
改为页顶横幅"系列设计还没定完，这份大纲缺少课程级依据"，点名缺什么并给入口。

**2）"前三步定完"用缺口判定，不用相位。** 相位只看目标与节点：方向可以为空、
目标可以没有证据，而 `seriesDesignPhase` 仍停在 `knowledge`。新增
`seriesDesignComplete(doc)` = 方向无缺口 + 课程目标无缺口（含证据 / 达标线 /
支撑知识点）。知识体系的"没有先修"之类是质量建议，不阻止继续——一门全是 intro
的入门课天然没有先修。

**3）大纲生成读系列设计。** `readSeriesOutlineAiContext` 多读一份设计快照，翻译成
提示词形状（方向、课程目标含可观察行为 / 最低达标线 / 证明方式、知识体系含难度 /
先修用名字）。三份模板新增「系列设计（课程级依据）」块，system prompt 明确
"与系列说明冲突时以系列设计为准"。设计没定完时提示词先写清缺什么、要求模型把
"这次只能按名称与说明生成"写进每条 note，而不是装作有依据。

**4）界面说清依据。** AI 对话框在生成前显示"依据系列设计：课程目标 N 条 ·
知识体系 M 个点 · 方向与目标已定"；没定完时显示缺口与系列设计入口。系列设计页的
第 4 步（大纲）在前三步未定完时禁用并给理由，步骤条在定完后三个都打勾、
"④ 大纲（驾驶舱）· 下一步"。

### 8.12 设计变了：指出哪些章 / 节 / 目还没跟上

§8.11 的已知代价是"设计改了之后，已生成大纲不会自动跟着变"。没有提示时，用户
改完设计回到驾驶舱会以为保存失败——大纲看起来一模一样。这一轮把"哪一层是哪一版
设计的产物"记下来，并在三个地方如实提示。

**1）记什么：内容指纹，不是时间戳。** 设计保存一次、内容却没变（重复提交、改回
原值）不该让整份大纲显示过期。新增 `canonicalSeriesDesign`（逐项写死字段与顺序，
集合字段排序：调换先修关系的书写顺序不算设计变更）与
`fingerprintSeriesDesign`（SHA-256 前 128 位）。迁移 18 加三列：
`curriculum_series.design_updated_at`（设计最后保存时间，界面说"什么时候改的"）、
`curriculum_series_outline_node.design_fingerprint` 与
`curriculum_task.design_fingerprint`（生成那一层时的指纹）。

**2）谁写指纹。** 只有 AI 生成路径写（`applySeriesOutlineAiPlan` 把当前指纹带进
每一行）；手写、大纲导入留空。空表示"不是从设计派生的"，**不参与**过期判断——
对来源不明的内容喊过期，用户没法用"重新生成"消掉它，只会变成噪声。人改过标题或
交底的那一行会清空指纹：它已经被改对了，不该继续显示旧版（只挪顺序不算改内容）。

**3）三个地方说同一件事。** 一个服务端读数 `readOutlineDesignDrift`（两条聚合
查询）同时供三处使用：
- 驾驶舱页顶横幅：设计更新时间 + 过期章 / 节 / 目数量 + 处理方式（重新生成，
  或直接改交底；已有目时章 / 节只能补新、不能覆盖重建）；
- 看板：章、节、目各自的「旧版设计」标记（`board-stale-badge`），按当前指纹逐行比较；
- 系列设计页：保存后的提示（`design-outline-drift`），避免"保存成功 ≠ 大纲已跟上"
  被误读；AI 大纲对话框在生成前也说明"只补空位不会更新已有旧版"。

**4）不做什么。** 不做自动重生成：覆盖重建会删掉人已经做的工作，而"哪些能安全
重建"要看每一目是否已开始设计，那是用户按层决定的，不是设计保存的副作用。
